# 021 · 交付不是“文件存在”，而是“目标环境可用”

2026-07-31

> **备注：截至目前，这是整个 `on-skills` 系列里最有含金量的一条洞察。**

## 这段小对话

来福谐波报告已经生成，也完整上传到了 GitHub。HTML 在本地浏览器中可以打开，Markdown、图片和其他交付物也都进入了版本控制；但真正从 GitHub 页面进入时，HTML 不能直接运行，最初那份内嵌大量 Base64 图片的 Markdown 也无法正常在线阅读。

用户追问：

> 为什么 Claude Code 可以帮我渲染，是不是加载了什么程序？

问题的关键不在于哪个模型“更会渲染”，而在于本地环境和 GitHub 是两个不同的交付环境：

- 本地 HTML 由浏览器运行；
- 本地 Markdown 可以由编辑器或预览器渲染；
- GitHub 仓库页面不会把普通 HTML 当作网站运行；
- GitHub 的 Markdown 渲染器也不适合处理体积过大、单行极长、内嵌大量 Base64 图片的文档。

这次真正做错的地方是：只验收了“本地能打开”和“文件已上传”，没有在用户最终点击、阅读和使用的 GitHub 页面重新验收。

## 最有含金量的洞察

> **交付物不是那个被生成或上传的文件。交付物是用户在真实目标环境中能够打开、看懂、复核并继续使用的结果。**

这条判断把很多过去被混在一起的“完成”拆开了：

```text
文件生成成功
≠ 文件内容完整
≠ 文件已经上传
≠ 目标平台能够渲染
≠ 用户能够顺利打开
≠ 用户能够看懂和使用
≠ 交付完成
```

命令成功、文件存在、哈希一致和本地预览正常，分别证明了不同环节没有出错，但没有任何一项可以单独证明最终交付已经成立。

## 为什么这比“最终文件要验收”更进一步

[018 · Skill 测试必须通过最终交付物验收](018-Skill测试必须通过最终交付物验收.md)已经提出：程序跑完、测试做完、文件生成，都不等于完成；最终文档还要经过内容、论证、图表和格式验收。

这次事故补上了更容易被忽略的一层：**最终文件也不能只在生产环境或制作者熟悉的工具里验收，必须在真实目标环境中验收。**

例如：

| 被验证的事实 | 实际只能证明什么 | 不能证明什么 |
|---|---|---|
| HTML 在本地浏览器打开 | 文件本身基本可运行 | GitHub 点击后可在线阅读 |
| Markdown 在本地预览正常 | 本地预览器能够处理 | GitHub 渲染器也能处理 |
| Git push 成功 | 对象进入远程仓库 | 用户看到的页面可用 |
| 文件数与哈希一致 | 备份没有缺失或变形 | 阅读方式正确、体验可接受 |
| GitHub API 返回文件 | 远程对象存在 | 页面正文和图片实际显示 |
| 自动化检查通过 | 已编码规则没有失败 | 未编码的人类使用问题不存在 |

专业交付必须准确说明每一种证据的证明边界，不能把上游成功静默升级为下游成功。

## Skill 应增加“目标环境验收契约”

可靠的 Skill 不只需要分析协议和输出协议，还需要第三套契约：

### 1. 分析协议

规定怎样取证、计算、提出竞争性解释并形成有边界的判断。

### 2. 输出协议

规定关键推理、数字、图表、来源和结论怎样出现在最终文档中。

### 3. 目标环境验收协议

规定最终用户在哪里、用什么入口、以什么权限和工具使用交付物，以及怎样证明它真的可用。

```text
分析协议
→ 保证判断尽量做对

输出协议
→ 保证判断被清楚写出

目标环境验收协议
→ 保证用户最终真的收到并能使用
```

三者缺一，能力都可能停在交付链的上游。

## 目标环境验收卡

以后每一种交付物都应先回答以下问题：

### 用户和入口

- 最终用户是谁？
- 他从哪里进入：GitHub、邮件、网盘、网站、Word、PDF，还是本地目录？
- 是否需要登录、授权、下载或安装额外软件？
- 链接文字是否准确描述了实际动作？

### 平台与格式

- 目标平台会预览、下载，还是执行这个格式？
- 是否存在大小、单行长度、脚本、字体、图片路径或权限限制？
- 本地可用的绝对路径、Base64、插件和登录状态，到目标环境后是否仍然成立？
- 是否应把“在线阅读版”“下载版”和“完整备份版”分开？

### 真实验收动作

- 是否从用户实际收到的入口重新打开？
- 是否检查正文、图片、表格、链接、目录和下载动作？
- 是否用目标用户的权限验证，而不只是制作者自己的高权限会话？
- 是否记录成功项、失败项和仍未验证项？

### 说明与降级

- 如果平台不能直接运行，是否在最显眼位置写明打开方法？
- 如果必须下载，是否明确写“下载后用浏览器打开”？
- 如果无法完成线上验收，是否如实写“已上传，目标环境未验证”？
- 是否提供一个更稳妥的替代格式或入口？

## 来福谐波案例怎样修正

这次最终采用的是：

- 只维护一份 GitHub 原生 Markdown，图片使用仓库内相对路径；
- 移除 Markdown 中的 Base64 图片，把文件从约 4.51 MB 降到约 167 KB；
- 保留自包含 HTML，作为下载后本地阅读版；
- 在 README、Markdown 和 HTML 开头同时说明 HTML 必须下载后打开；
- GitHub 链接明确区分“Markdown 在线阅读”和“HTML 下载页面”；
- 推送后实际打开 GitHub `main` 页面，验证正文和 22 处图片全部加载成功。

这里最重要的不是某一种具体修复方式，而是完成标准发生了变化：

```text
过去：文件已生成 + 文件已上传

现在：
文件已生成
→ 内容已验证
→ 已进入目标平台
→ 从真实入口打开
→ 按用户路径完成阅读或下载
→ 关键内容实际显示
→ 使用说明与边界清楚
→ 才算交付完成
```

## 对所有 Skill 的普遍意义

这条规则不只适用于 GitHub：

- PDF 生成成功后，要检查字体、分页、图片和可复制性；
- Word 生成成功后，要用目标办公软件检查目录、批注和版式；
- PPT 生成成功后，要在实际投屏比例下检查字号、裁切和动画依赖；
- 网站部署成功后，要从生产网址检查权限、移动端和关键交互；
- 邮件发送成功后，要检查收件人实际收到的正文、附件和链接权限；
- 数据管道运行成功后，要检查下游使用者拿到的数据口径、刷新时间和异常提示。

因此，Skill 的测试对象不能只停留在“模型行为”和“文件内容”，还要覆盖完整的交付链：

```text
判断是否正确
→ 表达是否完整
→ 文件是否有效
→ 平台是否支持
→ 权限是否正确
→ 入口是否清楚
→ 用户是否真的能使用
```

## 这次得到的一句话

> **截至目前，最有含金量的洞察是：不要把上游成功当成下游成功。文件生成、内容完整、上传成功、本地可用和目标环境可用，是五个不同的命题。只有从最终用户的真实入口重新走完整条路径，并证明他能够打开、看懂、复核和使用，交付才真正完成。**
