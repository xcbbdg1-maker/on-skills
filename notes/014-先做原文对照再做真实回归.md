# 014 · 先做原文对照，再做真实回归

2026-07-29

这次持续修改一个由抽象文章沉淀出来的 Skill 时，我发现：

> 第一遍过筛，最有效的方法不是立刻找一份招股书喂给 Skill，而是自己同时通读原文和第一版 `SKILL.md`，逐段检查原文到底被保留了什么、又丢掉了什么。

直接用真实材料测试当然重要，但它更适合第二阶段。第一阶段要解决的，是原文有没有被正确解码。

## 两种测试解决的是不同问题

### 原文—Skill 对照：结构覆盖审计

它检查的是：

- 原文的重要概念是否进入 Skill；
- 行业触发有没有被泛化掉；
- 作者举的例子有没有被当成修辞删除；
- “可能、如果、但是”背后的分叉是否还在；
- 多个科目之间的逻辑连接有没有丢失；
- 结论有没有连接到后续动作或模型；
- 专家跳步有没有被还原成取数、反证和停止条件。

例如原文分别解释：

```text
原材料高 → 可能是备货或涨价预期
在产品高 → 可能是生产周期或交付堆积
库存商品高 → 要区分等待交付和卖不出去
```

第一版 Skill 可能保留了“原材料、在产品、库存商品”三个字段，却把它们的判断逻辑合并成一个通用的“存货增加原因池”。

真实招股书测试未必立刻暴露这个问题；逐段对照却很容易发现：字段还在，字段之间的逻辑边不见了。

### 招股书实跑：行为回归测试

它检查的是：

- Skill 会不会主动读取完整材料；
- 会不会真的取数和计算；
- 会不会把文字解释与数字交叉验证；
- 遇到缺失披露时是否诚实降级；
- 会不会执行已经写入的模型路由；
- 最终输出是否仍然偷懒或公式化。

这一步回答的是：

> 已经写进 Skill 的规则，AI 真实使用时会不会执行？

它不能高效回答：

> 原文中哪些规则从一开始就没有写进去？

## 为什么招股书不适合做第一遍过筛

一份真实招股书只能触发原框架的一部分。

如果目标公司没有明显存货、客户不集中、没有重资本开支，那么相关规则即使完全缺失，也不会在这次测试中暴露。

同时，实跑结果还会受到很多干扰：

- 招股书有没有披露相关数据；
- PDF、表格和脚注是否被完整提取；
- 公司所属行业和阶段是否触发对应判断；
- AI 是否凭通用知识临时补出了 Skill 没写的逻辑；
- 没有输出某项，是 Skill 漏了，还是材料本身没有信息；
- 本次上下文是否碰巧提醒了模型。

这些变量混在一起，会让问题定位变慢。

更危险的是：模型可能依靠自身知识输出一个看起来不错的答案，让人误以为 Skill 已经覆盖了相关逻辑。换一个模型、换一家公司或换一段上下文，遗漏才重新出现。

## 为什么自己通读仍然重要

AI可以做全文对比、搜索关键词和生成映射表，但人更容易感知：

- 哪一句看似普通，其实是作者多年经验的压缩；
- 哪个例子不是为了好懂，而是限定了适用行业；
- 哪个“也一样”继承了前文一整套判断逻辑；
- 哪个名词虽然出现了，但没有进入执行流程；
- 哪句话意味着后续应该调用另一个模型或 Skill。

因此，人的角色不是手工检查格式，而是判断原文中哪些内容具有认知权重。

## 一套更高效的固定顺序

以后从文章、访谈或课程沉淀 Skill，可以采用三阶段：

### 第一阶段：结构覆盖审计

```text
冻结原文和第一版Skill
→ 逐段切分原文判断单元
→ 建立原文—Skill映射
→ 标记遗漏、弱化、误写和错误合并
→ 恢复触发、分叉、证据、反证和动作
→ 回挂主框架
```

原文判断单元至少包括：

- 抽象判断；
- 行业例子；
- 科目/阶段分类；
- 条件和转折；
- 替代解释；
- 下游动作或模型；
- 边界和停止条件。

### 第二阶段：真实材料行为回归

```text
选择覆盖面合适的招股书/案例
→ 让Skill独立执行
→ 检查取数、计算、文字证据和模型调用
→ 区分材料缺口与执行缺口
→ 修改并再次运行
```

不同案例应覆盖不同模块，不能只靠一家公司验证整个 Skill。

### 第三阶段：反例与边界压力测试

```text
设计容易误判的相似信号
→ 检查Skill是否保留竞争性解释
→ 检查是否知道何时停止结论
→ 检查低等级证据是否被错误升级
```

例如：

- 存货上升既可能滞销，也可能旺季备货；
- 应付增加既可能是供应商融资，也可能是逾期没钱付；
- 供应商采购占比低，也可能存在关键零部件单一来源；
- 经营现金流改善，也可能来自增长放缓和去库存。

## 原文—Skill 映射表应该检查什么

可以固定使用：

| 原文单元 | 隐含逻辑 | 当前Skill位置 | 覆盖状态 | 缺失类型 | 修改动作 | 验证方式 |
|---|---|---|---|---|---|---|

覆盖状态可分为：

- 完整覆盖；
- 只保留结论；
- 只保留字段；
- 只保留例子；
- 逻辑连接丢失；
- 下游动作丢失；
- 完全遗漏；
- 被错误公式化。

这比单纯搜索关键词更可靠。一个词出现在 Skill 里，只能证明它被复制过，不能证明它会被正确使用。

## 两种测试不能互相替代

只做原文对照，可能得到一个结构漂亮但不会执行的 Skill。

只做真实材料测试，又可能因为案例没有覆盖全部模块、模型临时补全或数据缺失，漏掉大量结构问题。

因此最合理的顺序是：

```text
先检查有没有正确解码
→ 再检查解码后会不会执行
→ 最后检查执行时会不会误判
```

也就是：

```text
结构覆盖审计
→ 行为回归测试
→ 反例压力测试
```

## 这次得到的一句话

> **从抽象文章制作 Skill，第一遍最有效的不是立刻找真实材料实跑，而是把原文和第一版 Skill 放在一起逐段过筛。先确认知识有没有被正确解码，再用真实案例验证它会不会执行，最后用反例检查它会不会把经验误当公式。**
