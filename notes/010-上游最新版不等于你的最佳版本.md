# 010 · 上游最新版，不等于你的最佳版本

2026-07-29

这次产生了一个很实际的问题：

> 如果一个 Skill 是从 GitHub 下载并安装的，作者后来又更新了仓库，怎么保证本地 Skill 是最新的？

答案是：**单纯下载或安装，不能保证持续更新。**

大多数安装动作只是把某个时间点的文件复制到本地。作者后续提交了新版本，本地文件通常不会自动变化。除非 Skill 本身带有更新机制，或者另外建立了上游版本检查，否则“安装过”不等于“持续跟随”。

但更重要的问题是：当这个 Skill 已经被我改造过以后，是否还应该自动变成作者的最新版？

## “最新”其实有两种

### 上游最新

指作者 GitHub 仓库中的最新 commit、tag 或 release。

它回答的是：

- 作者最近改了什么？
- 当前公开版本到了哪里？
- 是否修复了问题或增加了能力？

### 对我最新

指在吸收上游变化以后，仍然保留我的判断框架、注释和使用习惯的当前版本。

它回答的是：

- 哪些上游变化适合我？
- 我的本地修改是否仍然有效？
- 新旧规则有没有冲突？
- 当前版本是否仍然最贴近我的工作方式？

这两种“最新”不能画等号。

> 上游版本可以更新，但我的最佳版本应该经过选择、合并和验证，而不是被覆盖。

## 为什么自动覆盖很危险

如果 Skill 从未修改，重新安装最新版通常没有太大问题。

但一旦开始定制，自动覆盖可能导致：

- 我的注释被删除；
- 已展开的实务判断重新被压缩成一句话；
- 本地新增的测试、证据等级和停止条件消失；
- 作者调整了章节顺序，与本地框架发生冲突；
- 上游修复了一个问题，却重新引入我已经解决的问题；
- 文件表面更新了，实际更不适合我。

因此，定制后的 Skill 不能再被当作“作者文件的缓存”，而应被当作一个分叉发展的知识资产。

## 应该维护三层，而不是一个文件夹

推荐结构：

```text
作者仓库 upstream
        ↓ 获取并比较
我的定制仓库 origin
        ↓ 验证并发布
本地安装副本
```

三层职责不同：

1. **upstream**：保留作者原始更新；
2. **origin**：保存我选择性合并后的定制版本；
3. **本地安装副本**：Codex、Claude Code 等工具实际读取的版本。

如果只有本地安装目录，没有 Git 历史、上游地址和基准 commit，就无法可靠判断作者更新了什么，也无法安全合并。

## 最少要记录哪些版本信息

每个从 GitHub 获得并继续定制的 Skill，至少记录：

```text
上游仓库 URL
上游分支、tag 或 release
上次同步的 upstream commit SHA
上次检查时间
本地定制 commit SHA
本地关键修改摘要
最近一次校验或真实案例测试结果
```

这些信息的作用不是装饰，而是回答：

- 我现在基于作者的哪个版本？
- 作者后来提交了多少变化？
- 哪些内容是作者的，哪些是我的？
- 如果合并失败，能否回到上一个可用版本？

“最新版”必须能落到一个明确 commit，而不能只写“已经更新”。

## 三种更新模式

### 1. 完全跟随上游

适合未做本地修改、只想使用作者版本的 Skill。

流程可以是重新拉取、更新或重新安装。但仍应优先跟随稳定 tag/release，而不是无条件追逐每个最新 commit。

### 2. 跟踪上游的定制分支

适合已经加入个人判断、工作流和案例的 Skill，也是目前最适合我的模式。

流程是：

```text
检查上游新提交
→ 与上次同步 commit 比较
→ 阅读差异
→ 分类变化
→ 选择性合并
→ 做结构与行为验证
→ 更新基准 commit
→ 发布到本地安装目录
```

### 3. 冻结版本

适合高度稳定、合规敏感或暂时不希望变化的 Skill。

固定在某个 commit，只监控上游，不主动合并。等需要时再做一次完整升级评估。

## 上游更新要先分类，不能直接合并

发现作者更新后，把变化分成四类：

- **直接吸收**：错误修复、兼容性修复、明确改善；
- **互补合并**：作者增加了新视角，本地框架可以吸收；
- **冲突判断**：上游规则与本地判断不同，需要人工选择；
- **继续保留本地**：作者删除或简化了本地仍然需要的内容。

这一步需要比较的不只是文字，还包括：

- Skill 的触发条件是否改变；
- 主框架和编号是否改变；
- 判断逻辑是否被压缩或展开；
- references、scripts 和工具依赖是否变化；
- 输出格式、停止条件和证据要求是否变化；
- 本地真实案例是否还能正常运行。

## 版本更新后必须验证“行为”，不只是文件

文本合并成功，不等于 Skill 更新成功。

至少检查：

1. YAML 和目录结构是否有效；
2. 主框架与测试映射是否完整；
3. 本地定制内容是否仍在；
4. 上游新增规则是否与旧规则冲突；
5. references 和 scripts 是否能被正确调用；
6. 用一两个代表性任务做回归测试；
7. 记录这次升级吸收了什么、拒绝了什么。

真正需要保持最新的是 Skill 的行为能力，而不是文件修改日期。

## 最适合的自动化：自动检查，不自动覆盖

可以定期检查上游：

```text
读取 upstream 最新 commit
→ 与已记录的 baseline commit 比较
→ 没变化则结束
→ 有变化则生成 diff 和影响报告
→ 通知我决定是否合并
```

通知应至少包含：

- 上游从哪个 commit 更新到哪个 commit；
- 改了哪些文件；
- 是否影响本地修改区域；
- 建议直接吸收、人工判断还是暂缓；
- 合并后需要跑哪些验证。

对于已经深度定制的 Skill，默认策略应该是：

> **自动发现更新，人工或受控合并，绝不静默覆盖。**

## 这次得到的一句话

> **从 GitHub 安装 Skill 只能获得一个时间点的副本。要同时保证上游新鲜度和本地判断力，必须把作者仓库、个人定制仓库和本地安装副本分开管理：记录基准 commit，定期比较上游，选择性合并并做行为回归。最新版不是作者最后一次提交，而是你确认过、合并过、验证过的最新可用版本。**
