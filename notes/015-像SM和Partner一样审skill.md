# 015 · 像 SM 和 Partner 一样审 Skill

2026-07-29

在通读原文和第二版 Skill 时，我逐渐意识到：

> 检查 Skill 不能像验收一篇整理好的文案，而应该像审计项目里的 SM 和 Partner 检查小朋友的作业一样，带着专业怀疑和足够的细致，不断问“真的吗”。

第一版可能过于抽象，第二版又会增加大量公式、步骤、reference 和模型路由。内容变多不等于 Skill 已经成熟。很多新问题，恰恰是在第二版“看起来很专业”以后出现的。

## 三种不同层级的检查

### Junior 式检查：写了吗

Junior 容易关注：

- 这个概念有没有出现；
- 这个科目有没有列入清单；
- 公式有没有写进去；
- 文件是不是完整；
- 输出格式是否好看。

这种检查有必要，但只能证明内容存在，不能证明判断有效。

### SM 式检查：真的能执行吗

SM 会继续问：

- 数据从哪里取？
- 招股书是否真的披露？
- 分子、分母和期间是否可比？
- AI看到触发信号后，真的会读取对应 reference 吗？
- 多个步骤有没有正确先后顺序？
- 缺少数据时会停止，还是会自行脑补？
- 计算完成后是否进入下一项判断？

SM 检查的是工作底稿能否被复核、重复和执行。

### Partner 式检查：结论真的站得住吗

Partner 更关心：

- 这个证据真的支持这个结论吗？
- 有没有同样合理但方向相反的解释？
- 哪个证据会推翻当前判断？
- 这个结论对投资决策到底有什么影响？
- 是否改变估值、条款、投后治理、融资计划或退出判断？
- 如果它不改变任何决策，为什么要做这项分析？
- 公开信息足够支持这种措辞吗？

Partner 检查的不是步骤数量，而是结论是否可辩护、是否重要。

## “真的吗”不是抬杠，而是专业怀疑

专业怀疑不是默认一切都是错的，也不是故意唱反调。它要求每个结论都回答：

```text
我看到了什么
→ 我为什么这样解释
→ 还有什么替代解释
→ 证据支持到什么程度
→ 什么情况下结论失效
→ 它会改变什么决策
```

可以反复追问：

- 这个概念真的被完整保留了吗，还是只复制了名词？
- AI真的会取数吗，还是依靠临时联想？
- 这段文字是事实、管理层解释、会计政策还是风险提示？
- 这个公式真的适用于这家公司吗？
- 这两个指标真的具有因果关系吗？
- 这个经验判断真的适用于当前行业和阶段吗？
- 这个阈值真的有依据吗？
- 说“逻辑不同”以后，真的调用了下游模型吗？
- reference写得很好，主文件真的会触发读取吗？
- 结果真的回填到主框架了吗？

## 第二版为什么仍然需要从头通读

第一版最常见的问题是遗漏和过度抽象。

第二版增加实际操作步骤后，会产生另一类风险：

- 公式很多，但所需数据根本无法取得；
- 步骤很多，却没有先后顺序和停止条件；
- 每个局部都正确，彼此却重复、矛盾或无法回填；
- reference越来越多，触发关系却断了；
- 行业经验被写成等号公式；
- 同一个原因被放进通用原因池，丢失了类别路由；
- 新测试与原来的主框架平行生长；
- 模型选择写了，真正的量化调用没有发生；
- 输出要求超过公开材料能够支持的颗粒度；
- Skill依赖模型自己补全关键逻辑。

所以第二版完成后，不能只检查新增段落。必须重新从头读完整个 Skill，理解它已经形成的内部系统。

此时原文仍然重要，但已经不是唯一标准。经过多轮修改后，Skill加入了证据等级、公式、模型路由、数据源边界和跨层联动，它已经成为一个新的判断系统。审阅者还要检查这个新系统自身是否一致。

## 边读边改比集中返工更有效

如果通读时发现问题，最好当场让 AI 修改，而不是积累几十个问题后一次性处理。

因为问题刚出现时，以下信息都还在眼前：

- 原文上下文；
- 当前 Skill 对应位置；
- 这句话承载的隐含逻辑；
- 相邻规则；
- 可能受到影响的其他层级和 reference。

即时修改后，还可以马上回读相邻章节，检查是否出现新的冲突。

更适合的节奏是：

```text
读一小段
→ 用自己的话复述AI将执行什么
→ 问“真的吗”
→ 模拟正常案例和反例
→ 检查数据来源
→ 检查证据能否支持结论
→ 检查是否调用下游测试
→ 当场修改
→ 回读相邻章节
→ 每3—5项修改做一次架构收口
```

这不是追求一次把 Skill 做完，而是保持每轮修改的因果链清晰。

## 一套 SM/Partner Review 清单

### 存在性

- 原文概念、行业例子、条件、分类和动作是否都已映射？
- 是完整覆盖，还是只留下了关键词？

### 可执行性

- 触发条件是什么？
- 必须取哪些数字和文字？
- 数据具体来自哪里？
- 公式和口径是否明确？
- reference是否被主文件直接触发？

### 推理完整性

- 是否从观察直接跳到结论？
- 是否保留竞争性解释？
- 是否规定反证和停止条件？
- 类别、阶段和行业是否有正确路由？

### 证据边界

- 事实、公司陈述、推断和待验证事项是否分开？
- 招股书能支持到什么程度？
- 哪些问题必须进入数据室或访谈？

### 决策相关性

- 测试结果回填到哪一层？
- 会改变收入质量、毛利、现金、估值还是退出判断？
- 是否触发下游模型或其他 Skill？
- 最终对应什么投资动作？

### 系统一致性

- 新旧规则是否冲突？
- 是否重复堆叠？
- 主文件是否过长？
- 是否需要拆入 reference？
- 修改理由、反馈账本和版本状态是否同步记录？

## Review 留痕也应该像底稿

每个重要 review point 可以记录：

```text
原文/当前规则
→ Review问题
→ 为什么存疑
→ 需要的证据或反例
→ 修改决定
→ 影响层级
→ 验证结果
```

这样“真的吗”不会只停留在聊天里，而会成为 Skill 的认知历史。

## 审阅完成的标准

不是“我已经读完了”，也不是“AI说校验通过”。

更合理的完成标准是：

- 重要结论都有证据来源；
- 重要信号都有替代解释；
- 关键步骤能被另一轮 AI 重复执行；
- 数据缺失时知道停止；
- 下游模型能够被真实触发；
- 局部修改没有破坏主框架；
- 正常案例和反例都能得到合理处理；
- 最终结论能够回答“所以投不投、多少钱、什么条款、怎么管”。

## 这次得到的一句话

> **审 Skill 要像 SM 和 Partner 审底稿：不满足于“写了吗”，还要持续追问“真的吗、凭什么、还有没有别的解释、数据拿得到吗、做完以后改变什么”。第二版越详细，越要重新从头通读，并在上下文还清晰时边读边改、及时收口。**
