# 021 · 框架是走过以后留下的路径

2026-07-31

## 这两段对话

> 我其实现在对于框架没有那么迷恋。我觉得第一性原理依然适用，只要你在那个工作场景下，思考足够深挖和发散，你就可以找到能解决当前问题的框架。山高万仞，只登一步。

进一步说：

> 所以我对于别人的 Skill 的框架，也没有那么迷恋。

这并不是否定框架，而是重新确定框架在工作中的位置：**框架不应当先于问题成为答案。它更像是持续解决问题以后，留下的一条可复用路径。**

## 框架是经验压缩，不是真理

一个成熟框架通常压缩了作者反复遇到的问题、踩过的坑和形成的取舍。它能降低搜索成本，提醒后来者不要遗漏重要方向，但它也天然带着作者当时的：

- 工作目标；
- 行业和公司阶段；
- 可取得的信息；
- 风险偏好；
- 工具条件；
- 对“完成”的定义。

脱离这些条件，完整搬用框架未必比没有框架更好。它可能让人很快填完一张表，却没有真正接近当前问题。

因此，框架更适合作为问题索引和待验证假设，而不是必须逐项服从的操作真理。

## 第一性原理不是拒绝前人经验

第一性原理也不意味着每次都从零开始，更不意味着前人的经验没有价值。它要求的是：当框架不能直接解释当前场景时，回到问题本身，继续追问：

- 现在真正要解决的是什么？
- 结果受哪些机制和约束影响？
- 相同现象还可能由哪些原因造成？
- 哪些证据能够区分这些解释？
- 此刻最小但有效的下一步是什么？

沿着真实问题持续深挖，局部的分析路径会自然出现。它可能与某个经典框架重合，也可能只取其中一部分，还可能形成新的组合。

这里最重要的不是给新路径命名，而是确认它确实解决了眼前的问题。

## “山高万仞，只登一步”是一种工作方法

面对复杂任务，人很容易先追求一张完整地图：先建立宏大框架，再希望所有细节都能归位。但真实工作往往不是这样展开的。

更可靠的顺序是：

```text
看清眼前问题
→ 找到最关键的机制或不确定性
→ 取得一小组能够改变判断的证据
→ 踩实当前一步
→ 根据新看到的地形决定下一步
```

这串文字不是要再制造一个新框架。它只是描述实际前进时留下的脚印。

山再高，也不能一次完成。复杂度不是靠先写出更复杂的目录解决，而是靠每一步都能获得新的信息，并让下一步比上一步更准确。

## 阅读别人的 Skill，最值得拿走的不是目录

过去容易把一个 Skill 的层级、编号和检查表当成它最重要的部分。现在更值得追的是：作者为什么会这样判断。

例如，真正有价值的不是 Skill 写了“关注应收账款”，而是作者为何会从应收账款继续想到：

- 收入是否已经兑现；
- 客户是否掌握更强议价权；
- 公司是否通过信用条件换取增长；
- 风险是否集中在少数客户；
- 期后回款能否支持当前收入质量。

同样，真正有价值的也不是写下“经销商采购增加”，而是知道为什么还要区分：

```text
公司向经销商销售
≠ 经销商向终端客户销售
≠ 终端客户安装使用
≠ 终端客户持续复购
```

这些从一个信号跳到下一组问题的能力，就是专家经验中的“逻辑跳步”。目录只是结果，逻辑跳步才是能够迁移到新场景的东西。

## 借用 Skill 时，应当把规则重新放回工作场景

看见别人 Skill 中的一条判断，可以继续问：

1. 它试图解决什么真实问题？
2. 它为什么要看这个指标或执行这个步骤？
3. 中间省略了哪些实务经验？
4. 这个判断需要哪些前提？
5. 哪些替代原因会产生相同现象？
6. 如果实际执行，需要取得什么数据和文字证据？
7. 换行业、阶段或数据源以后，它还成立吗？
8. 什么结果会证明这条规则不适合当前任务？

能回答这些，别人的框架就变成了可以吸收的经验素材；回答不了，它可能只是排版整齐的观点集合。

## Skill 不必先追求完整，应该先追求踩实

这也改变了制作 Skill 的顺序。

第一版可以借框架降低遗漏，但没有必要假装一开始就已经覆盖所有场景。更自然的方式是：

- 从一个真实问题开始；
- 把抽象判断还原成机制、证据和测试；
- 在真实材料中执行；
- 记录哪里跳步、误判或无法取证；
- 只在模式反复出现后，再沉淀成稳定规则；
- 让框架随着案例生长，而不是让案例服从预设框架。

这与 [013 · 公开框架不等于可执行 Skill](013-公开框架不等于可执行skill.md) 和 [016 · 把抽象判断变成测试](016-把抽象判断变成测试.md) 是同一条主线：前者强调解压别人的经验，后者强调把判断变成可执行测试；本文进一步强调，连框架本身也应该接受真实问题的检验。

## 需要保留的一点警惕

不迷恋框架，不等于只凭临场感觉。

如果每次都只解决眼前问题，却不记录路径、反例和失败，经验就无法积累，下一次仍会从头开始。第一性原理负责回到问题，Skill 负责保存走通的路径；两者并不矛盾。

真正需要避免的是两个极端：

- 用现成框架代替思考；
- 用“具体问题具体分析”逃避复盘和沉淀。

## 这次得到的一句话

> **框架是经验的压缩，不是思考的起点。面对真实工作，应先沿着问题、机制和证据踩实眼前一步；阅读别人的 Skill，也应提取其中被省略的逻辑跳步，而不是照搬目录。第一性原理让我们重新找路，Skill 则保存那些已经被真实问题验证过的路。**
