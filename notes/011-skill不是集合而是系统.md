# 011 · Skill 不是集合，而是系统

2026-07-29

这次我意识到一件更长期的事：

> 对我来说，我自己做的所有 Skill，最后都要能够互相依靠。

这意味着最终目标不是积累越来越多的独立 Skill，而是建立一套能够共同工作的个人判断系统。

单个 Skill 可以很强，但真实问题很少只属于一个专业视角。尤其是投研、求职、内容创作、商业分析这类任务，往往需要多个能力连续接力。真正有价值的不是“我有多少个 Skill”，而是它们能不能把信息和判断可靠地传给下一个 Skill。

## 互相依靠，不等于互相纠缠

最直接的做法，是在每个 Skill 里不断写：

- 遇到这个问题调用 A；
- 还要参考 B；
- 最后再交给 C。

但如果所有 Skill 都彼此引用，很快会出现：

- A 依赖 B，B 又依赖 A；
- 每次任务都加载大量无关 Skill；
- 同一规则在多个 Skill 中重复维护；
- 一个 Skill 更新后，不知道影响了谁；
- 每个 Skill 都想做完整结论，职责重叠。

所以，Skill 之间真正需要的不是“知道对方名字”，而是清晰的能力边界和交接协议。

> 每个 Skill 应能独立完成自己的专业任务，同时通过稳定的输入、输出和证据结构与其他 Skill 协作。

## 从收藏夹变成一条工作链

可以把 Skill 系统理解成几层：

```text
资料获取层
→ 事实核验层
→ 专业分析层
→ 综合决策层
→ 交付表达层
```

例如一个投研任务可以是：

```text
招股书/财报获取
→ 审计 Skill 检查会计可靠性
→ PEVC Skill 判断生意与现金质量
→ 行业/宏观 Skill 补充周期背景
→ 估值 Skill 判断价格
→ IPO Skill 判断退出窗口
→ 报告 Skill 形成交付
```

这里没有任何一个 Skill 独自完成全部工作。每个 Skill 负责一段，并把结果交给下一段。

## 每个 Skill 都应该声明六件事

以后设计 Skill，除了 description 和执行步骤，还应回答：

```text
【输入】需要什么材料和上游结论
【职责】负责回答什么问题
【边界】明确不负责回答什么
【输出】交付哪些结构化结果
【依赖】什么情况下必须或可以调用其他 Skill
【交接】结论满足什么条件后交给谁
```

如果这六件事不清楚，Skill 很容易变成“什么都能分析一点”的大杂烩。

## Skill 之间需要统一的判断包

下一个 Skill 不应该只接到一句模糊总结，例如：

> 这家公司收入质量一般，现金流需要关注。

它应该接到结构化中间成果：

```text
任务范围与数据截止日
数据来源
已确认事实
公开信息推断
证据等级
关键假设
无法验证事项
可能推翻结论的证据
当前判断
建议调用的下一个 Skill
```

这套“判断包”相当于 Skill 之间的共同语言。

最重要的是保持证据等级不变：

- 上一个 Skill 的事实，下一步可以作为事实使用；
- 上一个 Skill 的推断，下一步仍然必须是推断；
- 上一个 Skill 的待验证问题，不能经过一次交接就变成结论。

否则就会出现“结论洗白”：一个低置信度假设在多个 Skill 之间传递后，莫名其妙变成了确定事实。

## 依赖关系应该分类型

并不是所有依赖都一样。至少可以分为四种：

### 必需依赖

缺少上游结果就无法继续。例如估值 Skill 必须先取得可比口径的财务数据。

### 可选增强

没有也能完成，但调用后结论更完整。例如 PEVC 财报分析可接入宏观或行业周期判断。

### 下游交接

当前 Skill 发现问题后，不越界作答，而是把问题交给更合适的 Skill。例如发现收入确认异常，交给审计 Skill；判断完生意质量，再交给估值 Skill。

### 同行复核

两个 Skill 从不同视角检查同一问题。例如审计 Skill 检查数字是否可靠，PEVC Skill 检查这些数字代表的生意是否值得投。

把依赖分类后，系统才知道什么时候必须调用、什么时候按需调用、什么时候只是交叉验证。

## 需要一个编排层

如果每个专业 Skill 自己决定所有调用关系，整个系统会越来越复杂。

因此需要少数“编排型 Skill”或 Agent，负责：

1. 理解用户最终要解决的问题；
2. 判断需要哪些专业 Skill；
3. 安排先后顺序；
4. 传递标准判断包；
5. 发现证据冲突时要求回查；
6. 汇总最终决策，而不是简单拼接各段输出。

专业 Skill 负责深度，编排层负责路线。

编排层也不能吞掉专业边界。它不重新发明财务、审计或估值规则，只负责选择、连接和整合。

## 互相依靠后的版本问题

当 Skill 开始形成依赖网络，单个 Skill 的更新不再只是自己的事。

例如修改证据等级、输出字段或结论格式，可能影响所有下游 Skill。因此版本管理还要增加：

- 哪些 Skill 依赖这个输出；
- 接口是否向后兼容；
- 哪些联动场景需要回归测试；
- 本地更新后是否要同步调整编排层；
- 上游 Skill 的低置信度输出有没有被下游错误升级。

这意味着 Skill 版本管理最终会从“文件有没有更新”变成“整条工作链还能不能正确运行”。

## 建立个人 Skill 系统的顺序

不需要一开始就设计庞大的 Agent 平台。可以从现有资产逐步整理：

1. 列出所有 Skill 及其核心职责；
2. 标出输入、输出和边界；
3. 画出必需依赖、可选增强和下游交接；
4. 统一证据等级与判断包；
5. 找出重复规则，确定唯一维护位置；
6. 为高频任务建立少数编排流程；
7. 用真实任务测试整条链，而不只测试单个 Skill；
8. 某个 Skill 更新后，回归测试受影响的依赖链。

最终形成的不是一张 Skill 清单，而是一张能力地图。

## 这次得到的一句话

> **Skill 的价值不只在于单点能力，而在于能否进入一条可信的判断链。每个 Skill 是一个专业器官，稳定的输入输出、证据传递和交接规则是神经系统，编排层则负责让它们为同一个目标协同工作。**
