# 016 · 把抽象判断变成测试：制作与审计 Skill 的总方法

2026-07-30

> **定位：总方法。** 这不是某一种财务分析 Skill 的局部技巧，而是制作、审阅和迭代所有判断型 Skill 的共同方法。

这次持续修改 `pevc-financials-lens` 时，我意识到：做 Skill 和做审计很像。

> 再抽象的判断，也要理清背后的逻辑，找到可以执行的测试；拿到测试结果后，还要继续解释结果，最后才能得出有边界的结论。

这句话把此前几篇笔记连接成了一条完整主线：

- [007 · 专家经验的跳步逻辑](007-专家经验的跳步逻辑.md)解释专家为什么只留下结论；
- [013 · 公开框架不等于可执行 Skill](013-公开框架不等于可执行skill.md)解释怎样解码被压缩的经验；
- [015 · 像 SM 和 Partner 一样审 Skill](015-像SM和Partner一样审skill.md)解释怎样检查测试和结论是否站得住；
- 本文把它们统一成一套从抽象判断到行动结论的总方法。

## 总方法的完整闭环

```text
抽象判断
→ 拆解概念与因果机制
→ 提出竞争性解释
→ 推导每种解释应留下的可观察痕迹
→ 设计并执行测试
→ 取得测试结果
→ 解释结果、排除替代解释
→ 形成有证据边界的结论
→ 传导到决策、模型、条件或下一轮取证
```

真正困难的不是列一个指标，而是完成中间的转换。

例如，“这门生意没有经营杠杆”不能直接写进结论。必须继续追问：

- 规模扩大为什么理论上应当改善利润？
- 哪些成本是固定、变动或阶梯式的？
- 收入增长时，毛利、交付、研发、销售和营运资金怎样变化？
- 当前利润没有改善，是扩张期的前置投入，还是每增加一元收入都要同比增加人力、定制和垫资？
- 产品结构、客户结构、产能爬坡或会计口径能否构成替代解释？

由此才能设计增量毛利率、增量营业利润率、单位交付成本、销售投入产出、人员增长弹性和营运资金吸收率等测试。

## 测试结果不等于结论

这是整套方法最重要的边界。

“销售费用率上升”“应收增长快于收入”“存货周转放慢”都只是测试结果。它们可以提示问题，却不能自动证明：

- 产品没有竞争力；
- 收入造假；
- 客户不满意；
- 库存卖不出去；
- 商业模式没有杠杆。

从结果到结论之间，还必须经过：

```text
口径是否一致
→ 现象是否重大且持续
→ 是否符合行业和公司阶段
→ 有哪些竞争性原因
→ 哪些证据支持或推翻每种原因
→ 风险是否可逆、何时应当兑现
→ 当前证据最多允许说到哪里
```

因此，好的 Skill 不能把实务经验写成“看到 A 就等于 B”的公式。它应当告诉执行者：A 触发什么问题、怎样测试、什么情况下支持 B、什么情况下应转向 C，以及数据不足时必须停在哪里。

## 为什么它像审计

两者共享同一种纪律：

- 把抽象命题拆成具体认定；
- 为认定设计可重复、可复核的程序；
- 区分事实、解释、推断和待验证假设；
- 发现异常后追查原因，而不是停在现象；
- 保留替代解释、反证和停止条件；
- 让结论受证据范围约束。

但判断型 Skill 往往还要比审计多走一步。审计主要回答数字是否存在重大错报；投资、战略、运营类 Skill 还要回答：

- 数字背后的机制是什么；
- 机制能否持续、复制和放大；
- 风险是否可逆；
- 未来里程碑能否兑现；
- 结果应怎样改变估值、条款、资源配置或行动。

所以，“像审计”描述的是取证和验证纪律，不意味着所有 Skill 都只做合规判断。

## 判断型 Skill 的三个组成部分

### 1. 测试库

规定看到什么信号时启动什么测试，需要抓哪些数字和文字，使用什么公式，怎样跨期、跨表、跨来源复核。

### 2. 判断引擎

规定同一个结果可能对应哪些原因，如何比较竞争性解释，什么证据会增强、削弱或推翻当前判断。

### 3. 证据治理

规定来源强弱、结论支持度、重要性、适用范围、缺失数据处理和停止条件，防止假设在多轮分析中被悄悄升级成事实。

只有测试库，没有判断引擎，Skill 会变成机械检查表；只有判断引擎，没有测试库，Skill 会变成漂亮但无法执行的文章；没有证据治理，两者都会制造过度结论。

## 一张通用判断测试卡

以后遇到任何抽象判断，都可以要求 Skill 填完这张卡：

```text
【原始判断】要判断什么
【概念定义】关键词在当前场景具体指什么
【因果机制】为什么可能产生这一结果
【竞争性解释】还有哪些原因会造成相同现象
【触发信号】什么时候必须启动测试
【所需证据】数字、文字、合同、访谈、外部资料分别是什么
【测试程序】如何取数、重算、勾稽、比较和回溯
【测试结果】观察到了什么，不夹带原因判断
【结果解释】哪种解释获得支持，哪种被削弱
【反证条件】什么新证据会推翻当前解释
【停止条件】信息不足时最多说到哪里
【决策传导】改变什么主结论、模型、条件或下一步行动
```

这张卡不是要求每次报告都照抄十二个标题，而是要求 Skill 内部不能缺少这些思考环节。

## 审一个 Skill 时应当问什么

判断“是否覆盖”不能再问这句话有没有出现，而要问：

1. 抽象判断是否被拆成了可观察、可证伪的命题？
2. 真实材料出现信号时，Skill 是否会主动触发测试？
3. 数据从哪里取得，口径是否能够复核？
4. 是否保留竞争性解释，而不是把经验写成等号？
5. 测试结果与原因解释是否分开？
6. 数据不足时是否会停止，而不是脑补？
7. 结论是否真正传导到后续决策？
8. 实际执行失败后，是否会把问题写回 Skill？

只要其中一环缺失，Skill 就仍可能只是“知识压缩”，而不是可靠的执行系统。

## 总方法的完成标准

一次判断只有满足以下条件，才算完整：

- 抽象命题已经操作化；
- 测试可由另一轮 AI 或另一个人重复；
- 输入、公式和证据能够追溯；
- 测试结果没有被直接冒充成原因；
- 至少处理了一个合理的替代解释；
- 明确什么证据会推翻结论；
- 结论强度没有超过资料边界；
- 结果已经回填主框架并改变后续动作。

## 这次得到的一句话

> **制作判断型 Skill 的总方法，是把抽象经验还原为可证伪的因果命题，把命题编码为可复核的测试，再把测试结果经过竞争性解释和证据边界，转化为能够影响决策的结论。Skill 不是结论仓库，而是一套从问题、证据到行动的认知程序。**
