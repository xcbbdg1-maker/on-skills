# 012 · Skill 修改不能只留下成品

2026-07-29

这次继续打磨 Skill 时，我意识到：

> 我对 Skill 提出过的所有修改文字，也应该单独沉淀成 Markdown 或修改日志。

一个不断被修改的 `SKILL.md` 只能告诉后来的人“现在是什么样”，却不能告诉他：

- 当时看到了哪段原文；
- 为什么觉得第一版不对；
- AI 漏掉的是词语、逻辑、执行还是边界；
- 隐含判断是怎样被还原出来的；
- 为什么最后选择这种写法；
- 哪些反例和替代解释曾经被考虑；
- 这次变化影响了哪些其他 Skill。

如果这些内容只留在聊天里，一旦换 AI、上下文压缩或隔一段时间再回来，Skill 的成长路径就断了。

## Git commit 也不够

Git 能保存文件变化，但 commit 往往只回答“改了什么”。

例如：

```text
add receivables test
fix cash-flow logic
update management expense section
```

这些信息不足以还原：

- 用户为什么提出问题；
- 原文的实务经验有什么跳步；
- 哪个旧规则会诱导 AI 偷懒；
- 新规则为什么要设停止条件；
- 这项修改属于13层中的哪一层；
- 为什么放进 reference 而不是主文件。

因此，版本历史和认知历史不是一回事。Git 保存 diff，修改记录保存判断。

## 应该同时保存三层资产

### 1. 当前执行版本

包括 `SKILL.md`、references、scripts、assets 和必要案例。

它负责回答：

> 现在执行任务时应该怎么做？

这一层要保持精炼，不应塞入大量开发过程。

### 2. 原始反馈账本

尽量逐字保存：

```text
日期
用户原话
引用原文
当时的质疑
关联 Skill
```

它负责回答：

> 这项修改最初是怎样被发现的？

原始文字非常重要。AI总结后的“问题描述”可能再次压缩用户已经捕捉到的微妙差异。

### 3. 修改决策日志

记录从反馈到执行文件之间的推理：

```text
当前覆盖
真实缺口
隐含判断逻辑
主层/联动层
修改决策
文件与章节
替代解释
停止条件
验证结果
版本与同步状态
```

它负责回答：

> 为什么最后这样改，而不是采用其他写法？

## 运行文件和开发历史要分开

不应把所有聊天和修改理由直接塞进运行中的 Skill。

否则会导致：

- 每次触发 Skill 都加载无关历史；
- 主文件越来越长；
- 当前规则与旧讨论混在一起；
- AI 不知道哪些是执行要求，哪些只是探索过程；
- Skill 从工具变成档案馆。

更合理的结构是：

```text
skill-source/
├── skill/                       当前可执行版本
│   ├── SKILL.md
│   └── references/
└── development/                 不进入运行包
    ├── feedback-ledger.md       原始反馈
    ├── decision-log.md          修改理由和结构决策
    └── protocol.md              固定修改协议
```

如果当前使用的是直接安装目录，开发记录也可以保存在独立的 sibling 目录，不与运行包混装。

## 每次修改都要创建一个 CR

为每项修改分配编号，例如：

```text
CR-20260729-014
```

同一个反馈导致多个文件变化时仍使用同一个 CR。以后补充同一判断，可以使用修订号：

```text
CR-20260729-014-R1
```

这样可以把下面这些内容串在一起：

```text
用户原话
→ 缺口判断
→ 层级映射
→ 文件修改
→ 验证结果
→ Git commit
→ 本地部署和GitHub同步状态
```

## 固定修改协议

以后每次修改 Skill，都执行：

```text
捕获用户原话/原文
→ 创建CR编号
→ 定位当前覆盖
→ 还原隐含逻辑
→ 映射主层/联动层
→ 决定修改、合并或拆入reference
→ 更新执行文件
→ 更新原始反馈账本
→ 更新修改决策日志
→ 运行校验和必要的回归测试
→ 记录版本与同步状态
```

完成定义是：

1. 执行文件已经更新；
2. 用户原话已经保存；
3. 为什么这样改已经记录；
4. 层级和依赖关系已经说明；
5. 校验已经完成；
6. 版本与同步状态已经记录。

> 没有记录“为什么改”，就不算完整完成一次修改。

## 回溯旧修改时要诚实标注缺口

现有 Skill 可能已经经过很多轮修改，但没有日志。

可以从聊天、当前文件、Git history 和 GitHub commit 回溯：

- 原文片段；
- 用户质疑；
- 最终判断；
- 层级编号；
- 文件变化；
- 当前验证状态。

但无法恢复的内容必须明确写明。例如运行目录没有 Git 历史时，不能编造 before/after commit；只能记录“历史 commit 不可取得”。

回溯记录应与实时记录区分。实时记录可以保存完整因果链，回溯记录只能尽可能恢复。

## 公开方法论与私有过程分开

`on-skills` 适合保存可迁移的方法论，例如：

- 为什么要记录修改理由；
- 如何维护主框架；
- 怎样追踪上游版本；
- Skill 之间如何传递证据。

具体 Skill 的原文、用户私有批注、逐项修改和内部判断，默认应留在本地或私有仓库。

这样既能公开方法，又不必公开所有知识资产和工作痕迹。

## 这套记录还会帮助 Skill 互相协作

当多个 Skill 形成依赖网络后，修改日志还需要回答：

- 哪些下游 Skill 使用了这个输出；
- 证据等级或字段是否变化；
- 是否需要更新编排层；
- 哪些依赖链需要回归测试；
- 上游更新是否覆盖了本地判断。

因此，修改日志最终不仅是历史档案，也是依赖治理和版本升级的依据。

## 这次的实际落地

本轮已经为 `pevc-financials-lens` 回溯建立:

- 原始反馈账本；
- 修改决策日志；
- 固定修改协议。

记录覆盖了收入质量、毛利率归因、硬科技毛利分叉、跨表联动、管理费用、经营现金流、Runway、应收兑现和坏账准备充分性等修改，也单独记录了架构收口、上游版本和 Skill 协作问题。

## 这次得到的一句话

> **Skill 的成品告诉我们现在怎么做，修改日志告诉我们为什么变成这样。只有同时保存用户原话、修改决策和版本变化，Skill 才不会在换 AI、换时间或追踪上游时失去自己的成长路径。**
