# 025 · 先用讲义学懂项目，再反向改造 Skill

2026-08-06

## 这次的观察

> 我一直以来好像都在用 AI 针对真实项目生成学习讲义。等我把讲义基本弄懂，项目也就懂了；项目懂了以后，我就能开始提出这个 Skill 应该怎么改、怎么做得更好的建议。

这不是偶然形成的使用习惯，而是一条稳定的学习与共创路径：

```text
真实项目与原始材料
→ AI 生成针对这个项目的学习讲义
→ 我阅读、追问、复算和纠错
→ 我逐渐弄懂项目的目标、口径、证据和判断链
→ 我开始发现遗漏、跳步、错配和真正重要的完成标准
→ 我提出对 Skill 的修改建议
→ AI 把建议产品化为可执行规则
→ 回到原项目或新案例验证
→ 失败和新问题进入下一轮讲义与 Skill
```

它最关键的地方是：**讲义不是项目完成后的附属说明，而是项目经验进入人脑、再从人脑进入 Skill 的中间层。**

## 讲义先训练人，人再训练 Skill

如果我还不懂一个项目，AI 即使生成了一份结构完整的 Skill，我也很难真正判断它好不好。

我可能看得出章节是否齐全，却看不出：

- 两个数字的口径能不能比较；
- 一个结论是否跳过了必要的中间步骤；
- 哪条异常只是表象，哪条会真正改变项目判断；
- 哪些事实只能用于这个项目，哪些规则能够迁移；
- AI 在什么地方应该继续取证，什么地方必须停止；
- 一份交付物到底是“写完了”，还是已经解决了问题。

学习讲义改变了这一点。AI 先把分散在申报表、底稿、合同、访谈、计算和交付物里的信息，重新组织成我能学习、追问和复核的结构。我不再只是接收一个答案，而是在恢复答案背后的项目模型。

例如，国家税务总局目前公开的 [A100000《企业所得税年度纳税申报主表》](https://12366.chinatax.gov.cn/bzds/056/056.html) 将第 36 行定义为“实际应纳所得税额（33＋34－35）”。只有真正弄懂税务申报与会计所得税费用的口径，才会指出：

> 申报表第 36 行不包含递延所得税，因此不能拿它与“当期所得税费用＋递延所得税费用”的所得税费用总额直接比较。

这类反馈已经不是“这里写得不清楚”，而是在告诉 Skill：比较对象怎样定义、什么情况下会形成假异常、应当怎样拆分和勾稽。表式还可能修订，因此真正应当进入 Skill 的也不是孤立的“第 36 行”，而是先识别表名、版本和行次定义，再判断两个口径能否比较。**项目理解一旦形成，用户的反馈就会从修改答案，升级为修改产生答案的方法。**

这也说明，我不必先成为抽象的 Skill 设计专家；判断力可以先从一个个具体项目里长出来。

## 好讲义不是摘要，而是认知脚手架

讲义如果只是把项目材料缩短、换成更顺的表达，它仍然可能让人产生“看懂了”的错觉。真正能帮助我学懂项目的讲义，应当保留从事实到判断的路径：

```text
项目要解决什么问题
→ 原始材料在哪里
→ 关键概念和口径怎样定义
→ 数字怎样计算、勾稽和比较
→ 从证据到结论经过哪些步骤
→ 还有哪些替代解释
→ 哪些地方资料不足
→ 结论最终改变什么动作或交付物
```

因此，讲义的完成标准不是“AI 写完了”，而是我能做到几件事：

1. 用自己的话解释项目为什么这样做；
2. 回到原始材料找到关键证据；
3. 复算或复现核心判断；
4. 发现口径错配、逻辑跳步和证据不足；
5. 把同一判断迁移到一个相似或相反的案例。

如果只能复述讲义里的结论，项目还没有真正进入我的判断系统。

## 人与 AI 的分工会在闭环中发生变化

在项目开始时，AI 可以先发挥材料处理和知识组织的优势：广泛阅读材料、整理概念、搭出解释结构、追溯来源，并把复杂过程拆成可以学习的步骤。此时它更像执行者和讲解者。

随着我通过讲义弄懂项目，分工开始变化。

我负责：

- 判断什么问题真正重要；
- 质疑看似合理但口径不一致的比较；
- 用实务经验识别 AI 省略的步骤；
- 决定哪些能力值得固化，哪些只是一次性处理；
- 确认结论、边界和完成标准。

AI 负责：

- 把我的自然语言反馈还原成明确缺口；
- 扫描 Skill 中是否存在同类问题；
- 把建议编码为触发条件、判断链、取证步骤、反例、停止条件和输出协议；
- 修改执行文件、测试和开发记录；
- 用原案例、对照案例和反例做回归。

这不是“人提出灵感，AI 负责写文件”这么简单。人的作用是提供已经经过项目学习校准的判断；AI 的作用是把判断工程化、系统化，并检查它能否稳定复现。

## 一次真实项目，最好留下三层产物

每个值得深入学习的项目，不应只留下最终交付物。

### 1. 项目交付物

回答这一次任务得出了什么结论、完成了什么工作。它首先服务当前项目。

### 2. 项目学习讲义

回答这件事为什么这样做，关键概念、证据、计算、判断链和边界是什么。它服务人的理解。

### 3. Skill 进化记录

回答从这次项目发现了哪些可迁移缺口，最后决定修改什么、暂缓什么，以及怎样验证。它服务未来的重复执行。

三层不能混在一起。客户名称、具体金额和一次性事实应留在项目材料；讲义可以保存匿名化的判断过程；只有被理解、被抽象并经过案例验证的部分，才应进入 Skill。

这也承接了 [006 · 交付物是给人脑加工的坯料](006-交付物形态与skill协作.md) 和 [012 · Skill 修改不能只留下成品](012-skill修改不能只留下成品.md)：可锻的 Markdown 让人继续思考，反馈账本与决策日志则保存理解怎样变成了规则。

## 不要跳过讲义，直接让 AI 自己造 Skill

如果项目还没有被人真正弄懂，就让 AI 同时生成 Skill、运行 Skill、再评判 Skill，很容易形成一个自我确认的闭环。模型可以把通用知识写得很完整，却没有独立判断者指出：它抓错了口径、遗漏了实务步骤，或者把一次性处理误当成通用能力。

但另一边也不能把我的每一句意见原样塞进 `SKILL.md`。项目中的直觉仍要经过一次产品化翻译：

```text
用户原话
→ 它暴露的真实问题
→ 适用场景与触发信号
→ 背后的机制和比较口径
→ 需要取得的证据
→ 替代解释与反例
→ 信息不足时的停止条件
→ 对输出和行动的影响
→ 用什么案例验证
```

这里与 [007 · 专家经验的跳步逻辑](007-专家经验的跳步逻辑.md) 和 [016 · 把抽象判断变成测试](016-把抽象判断变成测试.md) 是同一条主线：理解不能只留下观点，必须继续变成能触发、能取证、能证伪、能停止的执行程序。

## 什么应该进入 Skill

项目中产生的认识可以先分成三类：

| 类型 | 去向 |
|---|---|
| 只对当前客户、数据或文件成立的事实 | 留在项目材料与讲义 |
| 看起来可迁移，但还没经过其他案例验证的判断 | 进入待验证清单或开发记录 |
| 已说清机制、边界，并通过案例回归的判断 | 进入 Skill、测试与输出协议 |

这一步很重要。Skill 不是项目知识的全集，而是从项目中抽取出来、以后还能可靠执行的那部分路径。

## 一套可以重复使用的工作协议

以后做一个值得深入学习的项目，可以固定执行：

```text
完成或推进真实项目
→ 生成锚定原始材料的学习讲义
→ 按讲义共读、追问、复算和纠错
→ 由我用自己的话复述项目模型
→ 捕获我对结果与方法的修改意见
→ 区分项目事实、待验证判断和可迁移规则
→ AI 将选中的建议产品化
→ 记录用户原话与修改决策
→ 用原项目回归
→ 再用至少一个对照或反例检查迁移边界
```

它也补充了 [008 · 边读边锻造 Skill](008-边读边锻造skill.md) 与 [021 · 框架是走过以后留下的路径](021-框架是走过以后留下的路径.md)：边读边改解决的是怎样保持理解连续；这篇进一步说明，为什么人会在阅读项目讲义的过程中逐渐获得改造 Skill 的能力。框架不是 AI 预先替我写好的目录，而是我和 AI 共同走过、学懂并验证项目以后留下的路。

## 这次得到的一句话

> **我不是先学会怎样设计 Skill，才去理解项目；而是先让 AI 把真实项目变成我能学懂的讲义，再在弄懂项目的过程中获得修改 Skill 的判断力。讲义先训练人，人再训练 Skill；AI 最后把人的判断产品化，并送回真实项目验证。**
